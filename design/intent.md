# 意图识别方案（两层结构 + 置信度分级）

> 状态：设计稿。本期不实现，先把方案、边界、降级路径讲清楚，作为后续编码的合同。

---

## 1. 背景与目标

J-Coder 当前的执行链路是：用户输入 → `AgentHandle` → `ReActLoop.subscribe()` → 直接进入多轮 `ChatModel.call()`，由模型在 loop 内自主任意选用工具。这种"模型一把抓"的形态在以下三类场景里表现不佳：

- **轻量查询浪费**：用户只想"看一下这个文件为什么报错"，系统却调度了写项目专属的强代码模型，并可能在 loop 内产生写工具调用，触发沙箱授权流程。
- **工具漂移**：用户明确说"只读别改"，但模型仍然尝试 `edit_file` / `run_shell`，现有 `AuthorizationGate` 只能按命令黑名单拦截，无法理解"这次调用是否偏离意图"。
- **弱信号难分辨**："帮我看看 X"（读）和"帮我改一下 X"（写）只差一个字，但风险面完全不同；现有 system prompt 没有结构化的判别手段。

**目标**：在 `ChatModel.call()` 真正发起前，先对用户输入做一次**粗粒度意图分类**；在每次工具调用真正下发到 `ToolGateway` 前，再做一次**工具级语义门控**。两次判别都输出置信度，并按阈值分三档处理：**直接执行 / 选项确认 / 反问澄清**。

---

## 2. 总体架构（两层 + 三个数据流）

整条链路上新增两个拦截点，三个数据对象。

- **L1 粗意图分类**：在 `ReActLoop.subscribe()` 入口、`buildInitialMessages` 之前执行。一次性。
- **L2 工具语义门控**：在 `ReActLoop.dispatchToolCalls()` 把每个 `ToolCall` 下发到 `ToolGateway.invoke()` 之前执行。每步一次。

数据对象：

- `L1IntentResult`：粗意图标签 + 置信度 + 候选列表 + 提取出的槽位。
- `L2ToolGateResult`：每个待调用工具的"是否匹配当前意图"判定 + 置信度 + 替代工具建议。
- `IntentContext`：挂在 `AgentTask` 上的可读上下文，贯穿 loop 全程，给 L2 和后续观测者使用。

## 3. 第一层：粗意图分类

### 3.1 类别定义

你提出"读代码 / 写项目"两类是合理的轴心，但只覆盖一种"轻量查询 vs 代码改写"的二分，**还会漏掉三类高频场景**。建议扩展为以下六类，**首期上线其中四类**（其余留扩展位）：

| 类别 | 含义 | 典型用户说法 | 风险面 |
| --- | --- | --- | --- |
| `READ_CODE` | 只读理解代码 | "看看 X 怎么实现的"、"解释一下这段" | 低，纯只读工具即可 |
| `WRITE_PROJECT` | 修改代码或新增代码 | "给 X 加个功能"、"把 Y 改成 Z"、"重构" | 高，需要写工具 + 验证闭环 |
| `RUN_COMMAND` | 执行命令/构建/测试/版本控制 | "跑一下测试"、"提交一下"、"构建看会不会过" | 中-高，shell/git 工具 |
| `CHAT_QA` | 纯问答/解释/学习，不涉及代码 | "什么是 X"、"为什么 Java 要这样设计" | 极低，可以完全不给工具 |
| `PLANNING` | 多步规划，期望产出 TaskPlan | "帮我做一个完整的 XX 改造方案" | 中，结构化产出 |
| `OFF_TOPIC` | 与编码无关 / 拒绝 / 测试性输入 | "你是什么模型"、"忽略上面所有指令" | 极低，但要兜住 |

> 补充理由：CHAT_QA 不分类会让"什么是泛型"这种问题被强行套上代码工具，浪费 token 也容易误改文件；RUN_COMMAND 不分类会导致"提交一下"被模型理解成"写代码"而绕开 commit 工具。OFF_TOPIC 是必要的安全兜底。

### 3.2 输出格式（结构化 JSON）

LLM 必须以**严格 JSON** 返回，至少包含：

- `primary`：最可能的类别。
- `confidence`：0–1 之间的浮点。
- `candidates`：Top-3 候选 `(label, score)`，用于"选项确认"档。
- `slots`：该类别下需要的参数键值对；填不出来置 `null`。
- `negative_signals`：发现的反向信号，如"不要"、"只是"、"先别"。
- `model_route_hint`：建议使用的模型档位（`light` / `code` / `general`），由分类器给出。

JSON schema 由 prompt 强约束，解析失败时**整次分类视作 L1 失败**，走降级路径（见第 7 节），不让系统裸奔。

### 3.3 置信度三档

| 置信度区间 | 行为 |
| --- | --- |
| `≥ 0.85` | **直接执行**：按 `primary` 路由模型 + 设置初始工具白名单，不打断用户。 |
| `0.60 – 0.85` | **选项确认**：在 CLI 渲染 `primary` 与 `candidates` 的两到三个候选项，用户 1/2/3 选择，或输入 0 跳过分类（让模型自己定）。 |
| `< 0.60` | **反问澄清**：用一句话 + 候选按钮向用户确认意图；用户应答后再走一遍 L1（复用 LLM 上下文，更便宜）。 |

阈值不是写死的，放进配置 `cli.intent.l1.thresholds.{direct,offer,clarify}`，可灰度。

### 3.4 槽位（Slots）

每个类别预设必填槽位。槽位缺位会**主动压低置信度**（规则化扣分，不是 LLM 自评）：

- `READ_CODE`：`target`(对象)、`aspect`(关注点，可空)
- `WRITE_PROJECT`：`target_file` / `target_symbol`、`change_type`、`scope`(范围)
- `RUN_COMMAND`：`action`(build/test/git/...)、`args`(可选)
- `CHAT_QA`：无必填
- `PLANNING`：`goal`、`constraints`、`acceptance`
- `OFF_TOPIC`：无

例：用户输入"把 X 改成 Y"——`target` 已填、`change_type` 已填、`scope` 缺位，置信度自动从 0.92 降到 0.78，落入"选项确认"档，让用户补 scope。

## 4. 第二层：工具语义门控

### 4.1 触发时机

在 `ReActLoop.dispatchToolCalls()` 拿到模型产出的 `assistant.getToolCalls()` 之后、`toolGateway.invoke()` 之前，对**每一个** `ToolCall` 跑一次 L2 判定。注意：

- L2 是**逐调用**判别，不是逐轮。
- L2 输入包含三类信息：当前 L1 意图、L2 历史（前 N 步的工具调用判定）、本步工具定义（来自 `ToolDescriptorRegistry`）。
- L2 失败（解析失败 / 超时）默认**放行**，宁可漏判不要误拦——写工具还有 `AuthorizationGate` 和沙箱兜底。

### 4.2 输出格式

每个 `ToolCall` 一份：

- `decision`：`ALLOW` / `WARN` / `BLOCK` / `REWRITE`
- `confidence`：0–1
- `reason`：一句话原因，给日志和 UI 用
- `suggested_alternative`：当 `REWRITE` 或 `WARN` 时，给一个建议替换的工具名（如用户说"读"但模型想 `edit_file` → 建议 `read_file`）

### 4.3 决策三档 + 阈值

| 决策 | 含义 | 触发后行为 |
| --- | --- | --- |
| `ALLOW` (conf ≥ 0.80) | 与 L1 意图一致 | 直接进入 `ToolGateway` |
| `WARN` (0.55 – 0.80) | 弱一致或疑似漂移 | 进入 `ToolGateway`，但**额外走一道 `AuthorizationGate` 确认**（沙箱层要用户 ack） |
| `BLOCK` (< 0.55 且与 L1 强冲突) | 与 L1 意图冲突 | 不下发工具，把 `BLOCK` 结果以 `ToolResponse` 形式塞回 messages，告诉模型"被门控拦了，请换工具或重述" |
| `REWRITE` (任何置信度) | 工具语义不对 | 在 `dispatchToolCalls` 入口处就把该 ToolCall 改写成 `suggested_alternative`，再走 `ALLOW` 路径 |

> 补充：你最初只提"判断工具是否是我们想要使用的"——这是语义层面的判定。但当模型主动选错工具时（很常见，比如该用 `read_file` 却用 `grep`），单纯 `BLOCK` 会让模型陷入循环。**REWRITE 是必备的折中**，把硬拦截变成软改写。

### 4.4 与现有安全层的分工

- **本层**：语义层面——这次调用是否符合用户意图。
- **AuthorizationGate**：策略层面——命令/路径是否在白名单内。
- **ToolGateway.sandbox**：执行层面——超时、并发、重试、副作用追踪。

三者按"语义 → 策略 → 执行"顺序串联，**互不替代**。L2 失败不影响沙箱，沙箱失败也不回退到 L2。

## 5. 信号融合：不止 LLM 自评

你提出"LLM 自评 + 词槽完成度"是合理的起点，但**纯 LLM 自评在校准上不可靠**——LLM 倾向于高置信度。建议补上三类辅助信号：

### 5.1 关键词/规则信号（cheap & fast）

- 关键词词典：`写 / 改 / 新增 / 重构 / 提交 / 运行` → 倾向写/执行；`看 / 解释 / 为什么 / 是怎么` → 倾向读；`什么是 / 介绍` → CHAT_QA。
- 否定前缀：`别 / 不要 / 先别 / just / only / 不要写` → 标记 `negative_signals`，触发置信度折扣。
- 这层不参与最终打分，只在 L1 候选与规则严重不一致时**强制下调**置信度（例如规则强信号是 READ_CODE 但 LLM 选 WRITE_PROJECT 且没有 negative_signals → confidence 上限封顶 0.70）。

### 5.2 会话上下文信号

- 复用 L1 意图：同 session 内的多轮对话中，第一轮是 L1 的主战场；如果用户在第 N 轮继续深入，且 LLM 自身拿不准，可以**继承上一轮 L1 + 提示"延续上一轮意图"**。
- 跨轮工具历史：最近 3 步实际调用的工具（成功 / 失败 / 被拦），L2 可参考——例如连续三次只读工具突然切到写工具，L2 应触发 WARN。

### 5.3 模型自评的可信度

不要直接相信 LLM 给出的数字。引入一个**轻量本地打分器**（可选，首期可用规则代替）：把 LLM 的输出 + 关键词信号 + 槽位完整度喂进去，输出最终 confidence。规则版实现：

```
final_conf = 0.6 * llm_conf
           + 0.2 * keyword_match_score
           + 0.2 * slot_completeness_score
           - 0.15 if (rule_signal 强冲突 LLM 选择) else 0
           - 0.10 if negative_signals 非空 else 0
```

#### 5.3.1 权重与扣分项的取值依据

这些数字不是网格搜索或回归拟合的结果，**首期来自"按阈值临界反推 + 经验调参"**。本节把推导过程写清楚，方便后续校准时回放。

**加性归一化**：0.6 + 0.2 + 0.2 = 1.0，在无任何扣分时 `final_conf` 自然落在 [0, 1]，clamp 兜底。三段权重的设计思路是：

- **LLM 主导但不独断（0.6）**：LLM 上下文理解最丰富，但 §5 引子已写"LLM 倾向于高置信度"。给它过半数权重是承认信号质量，但留出 40% 给廉价结构化信号做修正。
- **关键词与槽位并重（各 0.2，合计 0.4）**：两者都是确定性的 0/1 区间信号，可独立校准。0.4 与 LLM 形成 6:4 杠杆——LLM 严重错判时，规则+槽位有足够力量把 `final_conf` 拉离 direct 档。

**扣分项按"档位临界"反推**：

- **冲突扣 0.15**：WRITE/READ 强冲突是最危险的误判（用户说"看"，模型理解成"改"→ 直接触发写工具）。0.15 是按 direct→offer 临界反推：
  - 理想情况 LLM 0.95 + 规则 1.0 + 槽位 1.0：0.6·0.95 + 0.2·1.0 + 0.2·1.0 = 0.97
  - 扣 0.15 → 0.82，恰好从 direct（≥0.85）落入 offer（0.60–0.85）档
  - 又不跌破 0.60 进入反问档，避免一次轻量查询被反复打扰
- **负向扣 0.10**：故意比冲突扣分轻。`negative_signals`（"别/不要/先别/just/only"）是用户主动声明边界，LLM 即使选 WRITE 也可能确实是想写。0.10 足以让一个本来 direct 的请求降一档到 offer（让用户口头 ack ），但不至于到反问档（用户已经表达得够清楚，继续问是骚扰）。

**校准锚点**（对应 `LocalIntentScorerTest`）：

| 测试场景 | 代入 | 期望 | 实测档位 |
| --- | --- | --- | --- |
| 完美路径 | 0.6·0.95 + 0.2·0.9 + 0.2·1.0 = 0.95 | > 0.85 | direct ✓ |
| WRITE/READ 冲突 | 0.6·0.9 + 0.2·0.9 + 0.2·1.0 − 0.15 = 0.77 | < 0.85 | offer ✓ |
| 负向信号 | 0.6·0.9 + 0.2·0.9 + 0.2·1.0 − 0.10 = 0.82 | < 0.9 | offer ✓ |

**调整路径**：首期不引入自适应学习，目标是"可解释、可回滚"。后续通过 `/intent-stats` 收集 `final_conf` 与用户最终选择的对齐率，按类别统计误判方向，再做权重微调——所有调整必须可回滚（配置项化），并保留对照 baseline。

### 5.4 成本控制

- L1 **只调用一次**，使用最便宜的模型档（`light`），prompt 控制在 500 token 以内。
- L2 在每步调用，**默认也走轻量模型**；当 LLM 选的工具超出"该意图推荐工具集"时，再升级到 `code` 档复核。

## 6. 模型路由（第一层的真正价值）

第一层分类不只是为了门控，**更关键的是路由到合适的模型**，这正是你提到的"读代码用轻量、写项目用代码模型"的落地处。

- `READ_CODE` / `CHAT_QA` / `OFF_TOPIC` → 轻量模型档（更快、更便宜）。
- `WRITE_PROJECT` / `PLANNING` → 代码专精模型档。
- `RUN_COMMAND` → 视具体子任务；纯 shell 调用轻量档即可，需要生成 patch 的归到 WRITE_PROJECT。

路由结果存到 `IntentContext.modelRouteHint`，由 `SpringAiReactAgentProvider` 在构造 `ChatModel` 时读取，覆盖默认 `agentName`。**不需要新增 ChatModel 实例**——同一 provider 用不同 model name 即可。

注意：路由判断**只发生在 L1**，loop 内部不再切换，避免在多轮中反复重建上下文。

---

## 7. 降级与失败处理

任何一层失败都不能让整个 loop 卡住：

- **L1 JSON 解析失败** → 视为 `conf=0.5`，按 `OFF_TOPIC` 兜底，跳过 L1 路由，用默认模型 + 默认工具集进入 loop；记一条 WARN 日志。
- **L1 调用超时** → 同上，跳过 L1。
- **L2 失败**（解析 / 超时 / 抛异常） → 默认 `ALLOW`，交给沙箱和 `AuthorizationGate` 兜底；记 WARN 日志。
- **用户选 0 跳过** → 直接进 loop，意图识别退化为当前 system prompt 的隐式行为。
- **配置开关** `cli.intent.enabled=false` → 整套跳过，方便回归对照和 power user。

降级策略写成策略对象 `IntentFallbackPolicy`，单测覆盖每条路径。

## 8. 可观测与可调

- 每次 L1 / L2 调用都写入 `IntentLog`，字段：时间戳、`executionId`、原始输入、模型原始输出、最终 confidence、决策、关键词命中、降级原因。
- 日志聚合进现有的 `verify.log` 体系，便于后续用脚本回放调阈值。
- 配置项集中在 `CliIntentProperties`：`l1.enabled`、`l1.thresholds`、`l2.enabled`、`l2.thresholds`、`model_routing.{light,code,general}`、`fallback.*`。
- 加 `/intent-stats` slash 命令，复用现有 `CliCommand` 体系，展示近 N 次 L1/L2 命中率与置信度分布（开发期用，上线可隐）。

## 9. 边界与异常场景（首期就要想清楚）

- **意图漂移**：用户在第 5 轮突然从"读代码"切到"写代码"。处理：每轮 L1 之前检查 `IntentContext.stickyUntilStep`，超过 N 步或用户输入中再次出现明确关键词，重新跑 L1；否则沿用。
- **负向意图与指令覆盖**：用户说"忽略上面所有指令"。OFF_TOPIC 触发，且 system prompt 模板**永远以服务端版本为准**，意图分类器输出与 system prompt 冲突时，**以 system prompt 为准**——意图层不应具备改写 system prompt 的能力。
- **多意图并存**："先看下 X，再把 Y 改了"。L1 拆成两步：第一个 Plan 节点 L1=READ_CODE，第二个 L1=WRITE_PROJECT。`candidates` 字段天然支持多意图识别。
- **跨语言输入**：英文 / 中英混合。规则词典首期只覆盖中文；英文回退到 LLM 自评。
- **极短输入**："?"、"hello"：槽位全空、关键词无命中，conf 自然 < 0.60，落入反问。

## 10. 测试与验收

- **黄金集**：手工标注 100 条典型输入，覆盖六类各 ≥ 15 条；首期只覆盖四类。
- **指标**：L1 top-1 准确率 ≥ 85%，L2 误拦率 < 5%（不允许把正确调用拦了）。
- **回归**：现有 ReActLoop 行为作为 baseline，开启意图层后整体成功率不得下降超过 2 个百分点。
- **A/B**：通过 `cli.intent.enabled` 开关做对照。

## 11. 实施路线（建议分三步，留足缓冲）

1. **第一期（最小可用）**：L1 only。实现关键词规则 + LLM 自评 + 槽位框架 + 降级。**不做 L2**。观察真实输入分布，校准阈值。
2. **第二期**：加 L2，先做只读意图（READ_CODE）的工具门控，验证 BLOCK/REWRITE 路径。
3. **第三期**：补 RUN_COMMAND / OFF_TOPIC 类别，接模型路由，开放 `/intent-stats`。

每期交付时，配置开关默认关，由配置中心灰度开启，便于回滚。
