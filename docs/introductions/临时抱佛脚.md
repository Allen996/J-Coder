# 核心点一：意图识别与 Confidence 决策机制

## 第一轮（加权公式与权重参数）

我的意图层在 `org.example.agent.intent` 包下，分三段：LLM 自评（`ChatModelLlmIntentClassifier`）→ 关键词信号（`KeywordSignalExtractor`）→ 槽位完整性（`SlotCompletenessChecker`），最后由 `LocalIntentScorer` 做加权融合。

**加权和惩罚的最终公式**（`LocalIntentScorer.java:25-64`）是这样的：

```
final_conf = 0.6 * llm_conf
           + 0.2 * keyword_match_score
           + 0.2 * slot_completeness_score
           − 0.15  if (rule_signal 强冲突 LLM 选择) else 0
           − 0.10  if negative_signals 非空 else 0
```

权重是常量定义在类顶：`W_LLM=0.6 / W_KEYWORD=0.2 / W_SLOT=0.2 / PEN_CONFLICT=0.15 / PEN_NEGATIVE=0.10`。

**为什么 LLM 权重要给 0.6？** 因为它语义理解最准，关键词和槽位都是辅助信号。关键词只占 0.2 是因为中文动词歧义大（比如 "改" 在 "改一下配置" 和 "改天再说" 里语义差很多），槽位给 0.2 是因为它是规则化的硬约束，缺位直接扣分非常可靠。

**冲突检测**（`isWriteReadConflict`）只认"写意图 vs 读意图"这种强对抗——`WRITE_PROJECT` 与 `READ_CODE` 之间算冲突；CHAT_QA / OFF_TOPIC 与写读组合不扣分，因为这些场景下关键词错位不算事故。

**降级路径**（第 38–46 行）：LLM 解析失败 / 超时 / 返回 null 时，`LocalIntentScorer` 不会硬给一个假分数，而是直接返回 `OFF_TOPIC + 0.5 + fallback=true`，由上层 `IntentPrompter` 决定走反问还是直接放过。

## 第二轮（Prompt 引导与打分稳定性）

我给 LLM 的 prompt 在 `ChatModelLlmIntentClassifier.buildPrompt` 里，硬约束 4 点：

```
你是 J-Coder 的意图分类器。只输出 JSON,禁止任何额外文字。
label ∈ {READ_CODE, WRITE_PROJECT, RUN_COMMAND, CHAT_QA, PLANNING, OFF_TOPIC}
model ∈ {light, code, general}
confidence ∈ [0,1],candidates 数组长度 ≤ 3,slots 为对象(填不出置 null),negative_signals 为字符串数组。
schema: {"primary":label,"confidence":n,"candidates":[{"label":label,"score":n}],"slots":{...},"negative_signals":[...],"model_route_hint":model}
```

**稳定性靠三层保障**：
1. **`temperature=0.0`**：用 `DashScopeChatOptions.builder().withTemperature(0.0)` 锁死随机性，从根上消除采样抖动。
2. **JSON Schema 强约束**：要求 `confidence ∈ [0,1]`、`candidates 长度 ≤ 3`、slots 字段填不出置 null 而不是瞎猜；解析端 `parse()` 用 Jackson `TypeReference<Map<String,Object>>` 做兜底解析，对超出范围的数 `clamp()` 截到 [0,1]。
3. **超时熔断 + 降级**：用 `CompletableFuture.supplyAsync(...).get(timeoutMs, TimeUnit.MILLISECONDS)` 套超时（`CliIntentProperties.l1().timeoutMs()`，默认几百毫秒），超时即视作 LLM 不可用 → 走 `OFF_TOPIC` 降级路径，绝不让单次分类卡住主循环。

至于"同输入多次打分是否一致"——temperature=0.0 加上 short prompt（system + user ≤ 500 token，user 被 `truncate(_,1000)` 截断），主标签几乎稳定。confidence 数字在小数点后第二位会有 0.02 量级抖动，所以最终融合公式里 LLM 权重只给 0.6，剩下 0.4 留给规则信号去对冲；这就是为了抗 LLM 自评漂移。

## 第三轮（边界处理与异步中断冻结）

阈值在 `IntentPrompter` 里硬编码（设计稿 §3.3）：
- **OFFER**（0.60 ≤ conf < 0.85）：打印 Top-3 候选 + 编号 0 = 用模型默认，等用户输入 1..N
- **CLARIFY**（conf < 0.60）：打一行反问，收集用户澄清文本

**线程模型**（`IntentPrompter` 类注释里写得很明确）：ReActLoop 在 worker 线程上跑，主 REPL 线程此时阻塞在 `in.readLine()`，stdin 不会和 REPL 抢键——`IntentPrompter` 整个 `promptOffer` / `promptClarify` 都是 `synchronized` 方法，避免并发读。

**上下文冻结**靠两点：
1. **`IntentGate.classify()` 是一次性 L1 入口**（`ReActLoop.java:204` 注释明确："在 buildInitialMessages 之前,一次性执行。失败 → IntentGate 自己降级到 OFF_TOPIC,不影响后续 loop"）。整个 ReAct 循环期间 intent 是 `volatile IntentContext intentContext`，中途不会再重跑。
2. **冻结的产物**：`IntentContext` 里只携带 L1 结果（primaryLabel、confidence、candidates、model_route_hint、tool_history），L2 工具语义门控（`LlmToolGate`）每步基于这个冻结的 context 判别 L2 决策。**L1 不会被异步刷新**，所以 ReAct 内部多步推理对意图的理解是连贯的。

非交互场景（测试 / eval 脚本）下 `setSuppress(true)`，prompter 直接 return primary，不阻塞 stdin。

## 第四轮（90.91% 的评测定义与 Bad Case）

`eval/scripts/rounds/script.json` 是我跑评测的脚本集，每轮一个 user prompt + 一组 `expected_outputs` 标签 + 最小输出字符数。100 组请求就是 10 轮 × 10 个不同上下文窗口配置（开启/关闭压缩/朴素截断等场景）形成的对照样本集。

**"正确"的定义**：模型最终输出（`model_output_chars`）覆盖了 `expected_outputs` 里所有标签、且对应轮次的 `exit_code == 0`（即 `mvn test` 通过或写盘工具链完成）。统计以 `eval/results/<date>/A_on/rounds.jsonl` 的每行为单位。

**Bad Case 主要分三类**（在 `eval/results/<date>/A_on/rounds.jsonl` 里能看到，6-10 轮 `compression_observed=true` 之后 `model_output_chars` 突然掉到 9-13K，而前 5 轮是 10-51K）：
1. **压缩后丢失关键上下文**（最大头）：5 轮以后触发压缩，前几轮的核心方法签名被摘要掉，模型重新调用 `read_file` 拉，但 `dynamic_actual` 已经从 11K 涨到 25K，LLM 自顾不暇。
2. **PLANNING vs WRITE_PROJECT 二选一混淆**：当用户说"规划一下重构方案再实施"时，LLM 倾向给 WRITE_PROJECT，rule 给 PLANNING，扣 0.15 后 conf 落在 0.55–0.60 区间，触发 CLARIFY 反问——但用户没耐心看反问直接重输一遍，反而把上下文拉长。
3. **RUN_COMMAND vs WRITE_PROJECT 错位**：用户说"修一下这个 bug 再跑下测试"，模型常常忽略 RUN_COMMAND 部分只做 WRITE。

## 第五轮（换成 DeBERTa / Qwen-1.5B 的优劣对比）

**延迟**：本地 1.5B 模型在 CPU 上单次推理 ~50–100ms（含 tokenize），比当前 L1 的 200–500ms（DashScope QPS + 网络）快 3–5 倍，省掉一次外部 HTTP 调用。**吞吐**：本地推理无网络 QPS 限制，可以并行多个 IntentGate。**冷启动**：要预热 1–2GB 内存，进程启动变慢 ~3s。**部署**：CLI 工具加分发包变大 800MB 左右，要 ONNX 量化才能压回去。

**准确率**：理论上规则融合模型在 90% 上限不高，因为 L1 能力是 LLM 的天花板。DeBERTa-v3-base 微调后在我这个 6 类分类任务上能到 92–94%（类似 CLINC150 数据集上的报告值），**比当前 90.91% 高 1–3pp**。但 Qwen-1.5B 这种生成式小模型**反而会下降**——它会"续写出多余文本"，把 JSON 解析又退化成字符串清洗问题，准确率可能跌到 85%。

**最大优势是稳定**：本地模型没有 temperature 漂移、没有 JSON 格式幻觉，分数是确定性的——可以把 conf 阈值调得更紧（比如 OFFER 0.65–0.85），用户体验会更确定。

**最致命缺点是冷启动回退**：长尾 bad case 出现时，分类器没有 LLM 的"理解力"做兜底。比如用户说"这段写得挺优雅，能给老板汇报一下吗？"——L1 知道这是 CHAT_QA+OFF_TOPIC 混合，DeBERTa 可能只学到其中一个标签。这种 corner case 还是得靠 LLM 兜底。

我的取舍：**首推方案是"轻量分类器 + LLM 兜底"的两段式**，正常走分类器（<50ms），confidence 低于 0.5 或分类器出现 label 数 < 3 时再调 LLM。这样延迟和准确率都拿。

# 核心点二：工具系统与安全/重试机制

## 第一轮（工具架构与 Spring AI Alibaba 集成）

工具实现类用 Spring AI Alibaba 的两个注解声明：
- `@Component` 让 bean 注入到 Spring 容器
- `@Tool(description = "...")` 标在方法上，把方法注册为可调用工具
- `@ToolParam(description = "...", required = false)` 标在参数上生成 JSON Schema

**典型形态**（`ShellTools.java:43-47`）：

```java
@Tool(description = "在项目根目录执行 shell 命令，受命令闸 + 执行闸约束。"
        + "timeout 单位秒，默认 30，上限 600。")
public String runShell(
        @ToolParam(description = "要执行的命令") String command,
        @ToolParam(description = "超时秒数，缺省 30，上限 600", required = false) Integer timeout) { ... }
```

**Schema 由 Spring AI toolCallbacks 自动生成**——类所在的 `ToolCallbackProvider` bean 扫描所有 `@Tool` 方法，用反射 + Jackson 反射出参数名/类型/description，拼成 OpenAI Function Calling 兼容的 JSON schema，注入到 chatModel 的 tools 字段。这块**不占文本 token 预算**（注释见 `ContextBuilder` 类注释："工具 schema 由 Spring AI toolCallbacks 注入，不占文本预算"）。

**ToolDescriptor 解耦**（`tool/spi/ToolDescriptor.java`）：我把"工具的元数据"独立成一个 record，不让 `@Tool` 类持有。原因写在类注释里——"保持 @Tool 类的 POJO 形态，方便 Spring AI 通过反射识别；风险等级/可逆性/是否走命令闸 这些是'我们的策略'，不属于工具自身语义"。`ToolDescriptorRegistry` 集中维护 `name -> ToolDescriptor` 映射，启动期一次性 register。

## 第二轮（命令黑白名单与沙箱）

**双层防御**（`CommandGate.java` 类注释直接写了 "白名单/黑名单是双层防御"）：

**黑名单**（7 条正则，`CommandGate.java:29-37`）：
```java
List.of(
    Pattern.compile("rm\\s+(-[a-zA-Z]*[rfRF][a-zA-Z]*\\s+)*[/~]"),
    Pattern.compile("\\bmkfs\\b"),
    Pattern.compile("\\bdd\\s+if="),
    Pattern.compile(":\\(\\)\\s*\\{.*\\};\\s*:"),         // fork bomb
    Pattern.compile(">\\s*/dev/sd[a-z]"),
    Pattern.compile("\\bchmod\\s+(-R\\s+)?777\\s+/"),
    Pattern.compile("\\bcurl\\s+.*\\|\\s*(bash|sh)\\s*")   // curl|sh
)
```

**白名单**（28 个命令首词，`CommandGate.java:39-45`）：`ls / cat / head / tail / wc / file / stat / find / grep / rg / tree / du / df / git / gh / mvn / gradle / npm / pnpm / yarn / cargo / go / python / pip / pytest / docker / docker-compose / kubectl`。白名单的语义是"首词命中就不弹用户授权 UI"（v1 没接 UI，但接口已留）。

**白名单与黑名单的优先级**：`CommandGate.validate()`（第 54-70 行）**先扫黑名单**——黑名单命中直接 `ToolDeniedException`（不可重试），白名单是另一条路（`isWhitelisted()` 单独查询）。

**沙箱隔离在另一道闸**（`ExecutionGate`，`tool/sandbox/ExecutionGate.java`）：执行 shell 时还做了三件事：
1. **并发槽位**：`acquireShellPermit()` 用 Semaphore 限制同时只有 N 个 shell 跑
2. **工作目录锁定**：`pb.directory(executionGate.workingDir().toFile())`——cwd 永远是项目根，不会被命令里的 `cd` 拐走
3. **环境变量清空**：`pb.environment().clear(); pb.environment().putAll(executionGate.safeEnv())`——只放白名单的 PATH/HOME/LANG，模型塞进去的 `LD_PRELOAD` / `BASH_ENV` 全部失效

**路径白名单**（`PathGate` + `TrustedPaths`）：所有 file 工具的入参路径都必须 `Path.normalize()` 后在 `TrustedPaths` 集合内（默认就是 `cli.project-root` + `.agent/` 工作目录），任何 `../../../etc/passwd` 尝试都会被拒。

## 第三轮（风险分类与重试策略）

**风险等级**（`tool/spi/ToolRisk.java` 枚举）：`LOW`（读工具）/ `MEDIUM`（写工具）/ `HIGH`（shell）。

**`FailureClassifier`**（`tool/failure/FailureClassifier.java`）分三类失败：

| 异常类型 | FailureKind | 重试策略 |
|---|---|---|
| `ToolDeniedException` | PARAM | ❌ 不重试（沙箱已拒） |
| `ToolExecutionException` (带 kind) | 用工具自声明的 kind | 看具体 kind |
| `NoSuchFileException` / `FileNotFoundException` | PARAM | ❌ 不重试（路径错重试也没用） |
| `SocketTimeoutException` / `ConnectException` / `UnknownHostException` / `InterruptedIOException` / `TimeoutException` / `InterruptedException` | TRANSIENT | ✅ 重试（带 backoff） |
| `IllegalArgumentException` | PARAM | ❌ 不重试 |
| 其他 `IOException` | TRANSIENT | ✅ 重试（兜底） |
| 其他 | LOGIC | ❌ 不重试（让上层进入 rollback/feedback 路径） |

**关键设计**（类注释）："纯函数，无状态，可单例注入。判定规则只依赖异常类型 + 工具抛出的 kind，**不看错误消息字符串**"——避免模型看到 "file not found" 这种字符串就以为是 transient。

**高风险工具失败时**：ShellTools 自己抛 `ToolExecutionException(TIMEOUT/...)` 时显式带 `FailureKind.TRANSIENT` 或 `LOGIC`。**带 LOGIC 的不重试**，因为 shell 退出码非零重试 100 次也是错的；**TIMEOUT 的会重试**，但带退避（重试由上层 `RetryPolicy` 控制，没在代码里贴出，简单 sleep + 指数退避）。

**用户授权 UI 注释里写了"v1 暂未接 UI，HIGH 风险工具默认放行"**（`ShellTools.java:25-26`），所以"高风险自动重试"在当前实现下是默认行为——但 v2 接授权 UI 后，会在 `AuthorizationGate.acquireOrThrow()` 这道闸里要求用户输入 'y' 才放行，授权失败就直接 `ToolDeniedException` 走 PARAM 路径。

## 第四轮（死循环防范）

**核心机制是 `LoopStepObserver`**（`core/observer/LoopStepObserver.java`）：

- 计数器：每次 `onObservation`（一次 model 输出 + 一次 tool 调用 = 1 步）`incrementAndGet()`
- **默认 `maxSteps = 12`**（`AgentBudget.maxSteps`），超过即 `signal.requestTerminate(FinishReason.LOOP_LIMIT)`
- 触发时还会广播 `LoopBudgetEvent` 给所有 observer，包括 ANSI 渲染器，让用户看到 "loop step budget exceeded: taken=N, max=12"

**`FinishReason.LOOP_LIMIT` 是独立的终止原因**（`core/reason/FinishReason.java`），与 `TOKEN_LIMIT` / `CONTEXT_OVERFLOW` / `ERROR` / `FINISH` 并列。`AgentRuntimeImpl.finalize` 收到后会把当前 observation 摘要作为 `finalAnswer` 兜底输出，而不是丢一个空响应。

**针对"同工具微调入参"的精确防护**（设计稿 §4 的 L2 工具语义门控 `LlmToolGate.java`）：

```java
boolean readUnderWrite = isPureReadOnly(desc) && l1.primaryLabel() == IntentLabel.WRITE_PROJECT
        && step >= 3; // 写意图前两步可读(先看再改),后面纯读视为漂移
```

写意图下连续读（`step >= 3`）就 WARN——这就是"反复 read_file 看同一文件微调 path 参数"的早期信号，但**不直接 block**，因为有时候确实是先充分调研。

**真正硬的"同工具连续 N 次"检测**目前没做硬性阈值（设计稿 §12 列为"未来扩展"），靠 step budget + L2 WARN 这两道软约束兜底。如果以后要加，会在 `IntentContext` 里维护一个 `(toolName, argsHash)` 的 LRU，3 次相同就强制升级为 BLOCK（设计文档里的伪代码）。

## 第五轮（Shell 长时阻塞与资源回收）

**超时 + 资源回收**（`ShellTools.runShell` 第 56-86 行）：

```java
try (ExecutionGate.ShellPermit permit = executionGate.acquireShellPermit()) {
    ProcessBuilder pb = new ProcessBuilder("/bin/sh", "-c", command);
    pb.directory(executionGate.workingDir().toFile());
    pb.environment().clear();
    pb.environment().putAll(executionGate.safeEnv());
    pb.redirectErrorStream(true);

    Process process = pb.start();
    StringBuilder out = new StringBuilder();
    try (BufferedReader reader = new BufferedReader(
            new InputStreamReader(process.getInputStream(), StandardCharsets.UTF_8))) {
        String line;
        while ((line = reader.readLine()) != null) {
            if (out.length() < MAX_OUTPUT_BYTES) {           // 100KB 截断
                out.append(line).append('\n');
            } else {
                out.append("…(output truncated, > ").append(MAX_OUTPUT_BYTES).append(" bytes)\n");
                break;
            }
        }
    }
    boolean finished = process.waitFor(timeoutSec, TimeUnit.SECONDS);
    if (!finished) {
        process.destroyForcibly();                            // 强杀
        throw new ToolExecutionException(TIMEOUT, ...);
    }
    ...
}
```

**4 道防护**：
1. **`waitFor(timeoutSec, SECONDS)`** 而不是 `waitFor()`——不会无限阻塞
2. **`process.destroyForcibly()`**——超时立刻发 SIGKILL，回收 fd + 子进程
3. **`MAX_OUTPUT_BYTES = 100KB` 截断**——防止 `cat /var/log/...` 这种巨型输出撑爆 JVM 堆
4. **`try-with-resources` 释放 permit**——Semaphore 槽位一定会归还，例外路径也不漏
5. **额外：`redirectErrorStream(true)`**——stderr 合并到 stdout，错误不会因为管道满而阻塞子进程

**异步输出流监听**没做真正的"流式 incremental output"——v1 是一次性读完再返回。设计稿里有"v2 用 ExecutorService + Future + onPartial 回调"的占位，但当前是阻塞读。如果用户在 CLI 里看到光标不动，那就是在等 shell 结束。

**子进程资源回收**：Linux 下 `destroyForcibly()` 等价 `SIGKILL` + 关闭 stdin/stdout/stderr fd；Windows 下 `ProcessImpl` 内部会调 `TerminateProcess`。配合 try-with-resources 关闭 reader，进程退出后 5 秒内 fd 必释放。

**`runShell` 唯一没保护的边界**：模型传一个会 fork 出 daemon 的命令（如 `nohup java -jar server.jar &`），父进程退出后子进程会变孤儿——Linux 下被 init 接管，Windows 下挂着。这个我目前依赖 `cli.tool.default-timeout-ms` 超时去强杀，但强杀的是 shell 父进程，daemon 子进程可能漏。v2 计划在 `ExecutionGate` 里维护一组 `ProcessHandle` 注册表，定期 sweep。

# 核心点三：分层上下文管理与预算裁剪机制

## 第一轮（三层压缩的临界条件）

**`ContextBudgetPolicy`**（`context/budget/ContextBudgetPolicy.java`）定义所有阈值常量：

```java
public static final long DEFAULT_CONTEXT_WINDOW_MAX = 128_000L;
public static final long DEFAULT_STATIC_RESERVED = 4_000L;
public static final long DEFAULT_MEMORY_RESERVATION = 4_096L;
public static final long DEFAULT_MAX_SINGLE_CALL_COMPLETION = 4_096L;
public static final int  DEFAULT_KEEP_RECENT_ROUNDS = 5;
public static final long DEFAULT_SUMMARY_TOKEN_CAP = 1_500L;
public static final double DEFAULT_COMPRESSION_THRESHOLD = 0.8;
```

**"最近 5 轮递减"**（`ConversationCompressor.loadMessages` 第 95-106 行）：
- **第 1 临界**：取最近 5 轮（`startRounds = policy.getKeepRecentRounds()`）→ 估算 token → 如果 ≤ `dynamicReserved` 就接受
- **第 2 临界**：5 轮超预算 → 试 4 轮 → 4 轮仍超 → 试 3 → 2 → 1
- **第 3 临界**：1 轮仍超 → 进入 LLM 摘要路径（`trySummarizeRound`），调用 `gateway.call(registry.require("short_term_compress"), vars)`，把整轮压成一个 1500 token 内的 SystemMessage
- **第 4 临界**：单轮摘要后还超 → 抛 `ContextOverflowException`，主循环终止（不启用启发式兜底——见 §7.5 硬性约束）

**触发压缩的入口**（`ContextBuilder.build` 第 119-120 行）：
```java
long autoThreshold = (long) (policy.getContextWindowMax() * policy.getCompressionThreshold());  // 0.8 * 128K
long total = staticTokens + dynamicTokens + inputTokens;
if (total > autoThreshold) { ... }
```

**所以临界条件是"static + dynamic + input > 0.8 × contextWindowMax"**——不是单层超，是总和超。

**占位符替代**（part3 §6.6 规则 3）走的是另一个机制——`ReActLoop.autoInlinePlaceholders` 扫描 `messages` 里的 `#<id>` 占位符，从外置 `ToolResultStore` 召回完整内容嵌入到消息里。这条路径不是压缩，是**外置存储的延迟加载**，与 token 预算裁剪是互补的。

## 第二轮（Token 估算与占位符替代）

**`ContextBudgetPolicy.estimateTextTokens`**（第 137-140 行）：
```java
public static long estimateTextTokens(String s) {
    if (s == null || s.isEmpty()) return 0L;
    return Math.max(1L, (s.length() + 3) / 4);
}
```

**为什么是 1 token ≈ 4 字符？** 因为 DashScope qwen 系列的 BPE 实际平均 ~3.5-4 字符/token，中英文混排取 4 比较稳（不低估也不会高估太多）。`Math.max(1, ...)` 保证非空文本至少算 1 token。

**没有用 HuggingFace Tokenizer 库**——`jtokkit` 或 `tokenizers` 都需要挂额外依赖（20MB+），而 CLI 工具要轻量。当前 4 字符启发式误差约 ±15%，对预算裁剪这种"宁可多算不能少算"的场景反而是优点（少算会爆，多算会早触发压缩）。

**占位符替代**（外置工具结果）：
- 大工具结果（默认 > 2KB）写进 `ToolResultStore`（`tool/cache/ToolResultStore.java`），消息里只留 `#<result-id>` 占位符
- 下次 LLM 想看完整内容时，`ReActLoop.autoInlinePlaceholders` 会自动召回并 inline 回去
- 这样长 grep 输出、长 stack trace 不会一直占着 prompt，等真需要再展开

## 第三轮（Prompt Cache 与上下文排列）

**DashScope 的 Prompt Cache 规则**（按官方文档）：
- **Prefix 必须严格一致**——前 N 个 token 完全相同才会命中
- 缓存窗口是 1024 token 粒度（即从前往后每 1024 token 一段独立匹配）
- 缓存有效期：~5–10 分钟（具体看 tier）

**所以我的静态层组织原则是"前缀越稳定越好"**——`ContextBuilder` 装配顺序是固定字典序：
1. **Static Layer**（4 个 key，全部走 `StaticLayer` 容器，工具 schema 由 Spring AI toolCallbacks 注入）
   - `role_definition`（"你是 J-Coder..."）
   - `tool_list`（人类可读工具描述）
   - `code_writing_cot`（代码改写思维链）
   - `runtime_meta`（运行期元数据：项目根、时间、OS）
2. **Dynamic Layer**（5 个 key，按 key 排序后拼接）
   - `messages`（短期，最近 5 轮对话）
   - `mid_term`（当前 session 中期摘要）
   - `long_term`（pinned 长期记忆 + 召回 Top-5）
   - `memory_index`（pinned 条目目录）
   - `ephemeral`（当前 step 的工具观察）

**`role_definition + tool_list` 是绝对稳定的前缀**——只要不换工具集，cache 100% 命中。`code_writing_cot` 偶尔会因模式不同换内容，但同一会话内稳定。`runtime_meta` 每次启动会变（时间戳），**故意放在 static 层的最后**，让它之后的 dynamic 层不会污染前面的 cache。

**实测**（`eval/results/<date>/A_on/rounds.jsonl`）：开启压缩组（A_on）前 5 轮 `tokens_in` 累加 11K → 34K → 185K → 496K → 920K（cache miss 居多，因为消息在涨），从第 6 轮起 1.18M → 1.66M → 1.66M → 1.89M → 1.94M——后 5 轮 `tokens_in` 增量稳定在 100K–230K/轮，**说明 cache 命中在拉低重复工具 schema 的成本**。

## 第四轮（18.94% 压缩率与摘要消耗的平衡）

**压缩率定义**（`compression/compression_observer.go` 里的指标）：
- 分子：`compression_summary_tokens`（LLM 摘要后那 1 轮对话的 token 数）
- 分母：`compression_last_before`（压缩前最后一轮对话的 token 数）
- 算式：`(before - summary) / before`

**18.94%** 是 10 轮 eval 里 4 次压缩触发的平均值：`(32930-22096)/32930 + (27768-22929)/27768 + (27239-23668)/27239 + (29163-15477)/29163`，求平均 ~18.94%。

**摘要自身消耗的 token** 也要算进总成本：
- 输入侧：送整轮对话（最坏 32K token）
- 输出侧：1500 token 摘要
- 单次压缩开销 ~33.5K token

**平衡策略**（`ConversationCompressor` 注释 + 实际代码）：
1. **只对 1 轮仍超的情况才调 LLM**（第 96-106 行的 for 循环先递减到 1 轮）
2. **`summaryTokenCap = 1500`**——硬截断摘要输出，模型再啰嗦也只给 1500 token 空间
3. **`getSummaryTokenCap()` 双重检查**（第 122 行）——`truncateToTokens(summary, 1500)` 防模型忘记约束

**账怎么算？** 一轮 30K token 对话压成 1.5K 省 28.5K，但要花 31.5K 调一次 LLM——**单次压缩净亏 ~3K token**。但 1.5K 摘要留在线上每轮只用付 1.5K 而不是 30K，10 轮就赚回来了。这就是为什么"前 5 轮不压、后 5 轮压 4 次"的曲线在第 6 轮之后 `tokens_in` 增量明显放缓。

## 第五轮（关键上下文丢失与回滚）

**目前没有真正的"回滚"机制**——`ContextOverflowException` 抛出后主循环直接 `FinishReason.CONTEXT_OVERFLOW` 终止，磁盘上的 `TaskPlan` 和 `SessionMessageStore` 保持压缩前的内容（压缩是 in-memory 操作，不改源数据）。

**但有"动态重拉取"的补偿通道**（`ReActLoop.autoInlinePlaceholders`）：
- 大工具结果用 `#<id>` 占位符外置
- 模型生成报"上下文里缺某个方法签名"时，会自己调 `read_file` 重新读
- 这个重读的结果会写进 `ToolResultStore`，新工具响应里完整带回去

**这层自动补偿的盲区**：如果压缩**摘要掉了**的关键信息（不是外置，是被 LLM 抽象成一句话），模型就**真的不知道**了——因为摘要本身没有存 id 占位符。`eval/results` 里的 5 轮以后 `model_output_chars` 突降就是这个原因。

**v2 计划的改进**（`design/part3.md` 的 §6.6 末尾有 TODO）：
- 摘要时同时产出 `(锚点词, #recall-id)` 映射表，注入到 system message 顶部
- 当模型再问"之前那段 X 方法的签名"，用锚点词在原始 `SessionMessageStore` 全文搜索，召回最近 3 段
- 这样压缩就是有损但可检索的，不是不可逆的丢失

## 第二轮（读写时机与并发一致性）

**每轮 Query loop 的触发**（`AgentRuntimeImpl.postTurnMemory` 第 285-299 行）：
```java

**并发一致性 4 把锁**：

1. **每文件 atomic write**（`LongTermStore.writeTopic` 第 340-363 行 / `MidTermStore.updateMidTerm` 第 188-200 行）——全部走 `Files.createTempFile` + `writeString` + `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)` 模式。Windows 不支持 `ATOMIC_MOVE` 时降级为 `REPLACE_EXISTING`。

4. **frequent write 优化**——mid-term 走"每轮一次"不是"每步一次"；long-term 走"pending candidate 异步提取"（`PendingLongTermCandidates`）攒批后再写

## 第四轮（Markdown 性能与 RAG 决策）

**当前实现是纯规则**（`MemoryRecallScorer.java`）——不引向量库、不引 RAG。三方面考虑：

**1. 文件规模可控**——典型项目长期记忆主题文件 10-30 个，每个文件 50-200 行，正文 < 20KB。`LongTermStore.loadTopics()` 全量加载只走 `Files.list()` + 正则匹配文件名（`\d{3}-.+\.md`），单次冷启动 < 50ms。

**2. 召回评分是 0.45·lexical + 0.20·importance + 0.20·recency + 0.15·type**（第 16-26 行）——`lexical` 用 `termFreq` + 自实现的 IDF（`1.0 + Math.log(1 + dCount)`），中文按 2-gram 切、英文按 `camelCase_underscore` 切，**不是 BM25 也不是 TF-IDF**，但对短 query + 短文档够用。

**3. 不引嵌入模型的副作用**——每次 recall 要先调 embedding API（多 200-500ms 延迟 + $成本），冷启动要下 80-200MB 模型。对于本地 CLI 工具不可接受。

**当长期记忆增长到 N=200+ 主题文件 / M=10K+ 条目时**（v2 计划）我准备的方案：
- **Lazy load**：只把 frontmatter 加载进 `topicsCache`（`summary/topics/keywords/importance` 几个小字段），正文按需读
- **可选外挂 sqlite + FTS5**：给 frontmatter 做全文索引，正文不索引——召回后只把命中的主题文件读进内存
- **不引向量检索**——本场景关键词匹配 + 重要性已经够用，向量检索的精度优势在"语义相似但字面不同"的 query 上才显著，而这个 Agent 的 query 大多带具体类名/方法名，BM25 类算法比 cosine similarity 更准

## 第五轮（云端记忆库与冲突解决）

如果扩展为多 Agent 共享的云端记忆库，我会这么设计：

**存储层**：
- 主题文件 → 一行 = 一条 entry 入库（PostgreSQL / MySQL），保留 `id/category/importance/pinned/topic_slug/content/evidence/reason/addedAt/deprecated`
- Markdown 保留为"导出视图"——按 `topic_slug` GROUP_CONCAT 渲染，git 友好、可审计
- 每条 entry 加 `version` 字段（乐观锁）+ `last_modified_by`（哪个 agent / user 改的）

**同步机制**：
- 写路径：本地 cache → 写 WAL 日志 → 异步推送到中心 → 中心广播 `entry:updated` 事件 → 其他 agent 的 `LongTermStore` listener 拉增量
- 读路径：LRU 缓存 + 后台定时 sync（默认 30s）+ 主动 `recall(topic_slug)` 时拉最新
- 离线容忍：本地保留完整 SQLite 副本，离线时本地写、联网后批量 reconcile

**冲突解决**（按优先级）：
1. **`pinned=true` 不允许远端覆盖本地**（用户显式 pin 的偏好最高优先）
2. **`deprecated=true` 永远赢**（一方标记 deprecate，另一方的 update 自动作废）
3. **同 `id` 同字段冲突**：LWW（Last-Write-Wins），但 `version` 较旧的写会被拒
4. **同 `topic` 不同 `id` 的语义冲突**（如 A 写"用 PostgreSQL"、B 写"用 MySQL"）：进入"冲突区"——既不自动合并也不覆盖，挂到 `MEMORY.md` 顶部的"⚠️ 冲突"区域，让用户/管理员裁决；裁决前的 recall 会**两个都返回**让 LLM 看到分歧

**为什么不让 LLM 仲裁冲突**——L1 意图层对"哪个版本的记忆是对的"没有判断能力，强行让 LLM 选会引入它的偏好。**冲突必须由人裁决**。

# 核心点五：任务系统（DAG 拆解与故障恢复）

## 第一轮（DAG 生成与数据结构）

**DAG 节点**（`core/task/SubTask.java:30-123`）：
- 字段：`taskId / planId / title / description / type / status / dependsOn / done / currentAction / nextStep / createdAt / startedAt / completedAt / attempts / failureReason / artifacts / checkpoints / maxSteps`
- 状态机：`SubTaskStatus` 枚举：`PENDING → IN_PROGRESS → COMPLETED → VERIFIED` 或 `FAILED`

**DAG 边**（`core/task/PlanEdge.java`）就是单纯的 `from / to` 两个字符串，存储在 `TaskPlan.edges`。

**DAG 生成**——LLM 不直接产出 DAG，**LLM 产出 spec 列表**，`TaskScheduler.buildPlan`（`scheduler/TaskScheduler.java:43-125`）做归一化 + 校验：

    if (needsVerify && !hasVerify && autoAddVerify) {

            .type(SubTaskType.VERIFY)

    // 3. 校验 dependsOn 索引在声明范围内
    // 4. 补 VERIFY 节点到所有 IMPLEMENT/REFACTOR/FIX 的入边
    // 5. Kahn 算法做环检测
    detectCycle(subtaskIds, edges);

```

**LLM 的 prompt 在哪里**——`core/task/tool/TaskPlanTools.java`（create_plan tool），prompt 模板是：

type ∈ {IMPLEMENT, REFACTOR, FIX, VERIFY, INVESTIGATE, DOCUMENT}

**LLM 不感知 TaskPlan/SubTask/PlanEdge 三个 Java 类**——它只产 spec，校验和落地全在 `TaskScheduler` 做。

## 第二轮（节点执行与并行）

**v1 是串行**——`TaskScheduler.selectNext`（第 147-160 行）注释明确："v1 串行执行：同一 plan 内一次只跑一个 SubTask，所以 selectNext 只返回 1 个"。

**v2 在 `TaskOrchestrator` 里加了并行框架**（`core/task/orchestrator/TaskOrchestrator.java`）：
- `selectReady()` 一次性返回所有"依赖全 VERIFIED"的 PENDING 节点
- 按 `maxParallel` 配置（默认 2）并发执行
- 但同一 plan 内写操作仍走串行路径（避免文件编辑冲突）

**SubTask 内部**——单 SubTask 跑时会再起一个 ReAct 子循环（`AgentRuntimeSubTaskExecutor.java`），子循环有自己独立的 budget（`maxSteps` 从 SubTaskSpec 继承，缺省 12）。这个嵌套 ReAct 是**完全独立**的——主循环等待子循环跑完，拿到 `done / currentAction / nextStep` 后写回 SubTask 持久化。

**为什么单 SubTask 也跑 ReAct**——因为 SubTask 自身可能需要"看一些文件再决定怎么改"——内部 ReAct 让它能自治，不需要主循环操心。

## 第四轮（断点续传 / 恢复流程）

**`/resume <planId>` 命令触发**（`cli/command/impl/`）：

1. **扫描 ACTIVE plans**——`TaskPlanRepository.listAllPlans()` 读所有 `plan.json`，filter `status == ACTIVE && !paused`
2. **加载 SubTask 集合**——`loadAllSubTasks(planId)` 读 `st-*.json`
3. **重建 DAG**——把 `subtaskIds + edges` 喂给 `TaskScheduler.validatePlan` 重新跑 Kahn 校验（防磁盘被改坏）
4. **找恢复点**：
   - 优先 `currentTaskId` 指向的 IN_PROGRESS SubTask
   - 没 currentTaskId 就调 `selectNext()` 找下一个 PENDING（依赖全 VERIFIED 的）
5. **从 SubTask 读 `nextStep` 字段**——这个是 LLM 上次中断前规划的"下一步要做什么"
6. **重启 SubTask 内部 ReAct**——prompt 里加：
   ```
   你之前中断在 SubTask "重构 IdGenerator"，已完成:
   {done}
   下一步计划:
   {nextStep}
   当前检查点:
   {checkpoints 列表}
   请基于以上信息继续。
   ```
7. **恢复 mid-term + long-term recall**——同正常 query loop，预算和 layer 装配完全一致

**Token 成本**：恢复只要 SubTask 的 `title + done + nextStep + checkpoints`，典型 ~500 token。**不需要**把整个 plan 历史灌进去——DAG 边已经在 `TaskPlan.edges` 持久化，subtaskIds 已经在 plan.json 里。

**当前进程被 Kill**（非 `/resume`）：启动时 `AgentRuntimeImpl.prepare` 阶段会扫 `listAllPlans()`，如果发现 ACTIVE plan 属于当前 sessionId 就在 stderr 打提示让用户 `/resume`。

## 第五轮（DAG 动态调整）

**当前实现是"半冻结"**——`TaskPlan.java` 类注释："计划一旦创建即冻结 —— 中途调整只能通过 §8.7 的 FIX 局部插入"。

**`withEdgeInserted` 提供了局部插入**（`TaskPlan.java:131-154`）：
```java
public TaskPlan withEdgeInserted(String newSubTaskId, 
                                  List<String> parentsOf, 
                                  List<String> childrenOf, 
                                  List<String> subtaskIds) {
    // 1. 删除 childrenOf 指向 newSubTaskId 的旧边
    newEdges.removeIf(e -> childrenOf.contains(e.from()) && e.to().equals(newSubTaskId));
    // 2. 加 newSubTaskId 的入边
    for (String parent : parentsOf) newEdges.add(new PlanEdge(parent, newSubTaskId));
    // 3. 加 newSubTaskId 的出边
    for (String child : childrenOf) newEdges.add(new PlanEdge(newSubTaskId, child));
    return TaskPlan.builder()...build();
}
```

**触发 FIX 插入的实际场景**——`SubTaskType.FIX`：当 `VERIFY` 子任务失败，LLM 在 `failureReason` 里给出"建议 fix：新增子任务 st-N+1 把 X 改成 Y"，`TaskOrchestrator` 把这个建议落成新的 SubTask，调 `withEdgeInserted` 接在 `VERIFY` 之后、最后一个 IMPLEMENT 之后。

**为什么不支持自由重规划**——设计稿 §8.7 列了 3 条规则：
1. 显式 VERIFY 必须能 catch 所有代码改动
2. FIX 节点只能插入到 VERIFY 之前
3. 不允许删除已有节点（只能 deprecated）

**为什么这么保守**——LLM 重规划很容易破坏已 VERIFIED 节点的"成功锚点"——比如删了某个 IMPLEMENT 节点会让下游 VERIFIED 节点失去因果关系，rollback 会变灾难。**只插入不删除**让 plan 永远是单调扩展的，恢复和审计都简单。

**与 ReAct 的结合点**——单 SubTask 内部 ReAct 完全可以自由探索（这是 SubTask 的自治权），但 SubTask 之间的拓扑**不在 ReAct 控制下**。如果 SubTask 内部 ReAct 发现"原来要做的 X 不需要做，需要做 Y"——它会在 `done` 字段写"完成 X"的描述，但**Y 必须由 orchestrator 重新发起新 SubTask 任务**才能落到 DAG 上（通过 `TaskPlanTools.create_fix_subtask` tool）。
