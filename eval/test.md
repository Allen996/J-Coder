# 上下文压缩能力训练集设计方案

> 本文件用于评测 J-Coder 的上下文压缩能力是否能在长会话中保持目标不丢失。所有内容仅以自然语言描述，不涉及具体代码。

---

## 1. 设计目标

构造一组包含十轮长上下文对话的训练样本，使得：

- 每一轮对话在执行后都会让当前会话上下文显著增长，足以触发 J-Coder 的压缩机制（静态层 + 动态层摘要）。
- 十轮累计之后，被压缩过的对话必须仍然能够继续推进，直到完成最初设定的代码修改目标。
- 通过"压缩前 / 压缩后"两组对照实验，量化压缩对任务完成质量与 token 消耗的影响。

最终回答三个核心问题：

1. 压缩是否会让模型在长程对话中丢失原任务目标（漂移 / 遗忘）？
2. 压缩对完成任务所需的 token 总消耗是节省了还是反而增加了？
3. 压缩后的会话是否还能稳定驱动工具调用并完成多文件代码修改？

---

## 2. 模拟项目场景

为了让十轮对话都有"真实可改"的代码作为载体，建议在 `eval/fixtures/mock-project/` 下放置一个小型多文件 Java 项目作为受试对象。建议项目结构（仅描述，不写代码）：

- 一份 `pom.xml`，声明一个不依赖 Spring 的普通 Java 工程。
- 三个核心源文件，描述一个"命令行记事本"工具：
  - `Main.java`：入口，负责解析命令行参数并分发到子命令。
  - `NoteStore.java`：负责在内存中保存笔记列表，并提供增删改查接口。
  - `CommandHandler.java`：负责把解析后的参数映射到 `NoteStore` 的具体方法。
- 配套的测试文件 `NoteStoreTest.java`，包含若干单元测试。
- 一份 `README.md`，简短描述当前命令行记事本支持哪些子命令。

这个项目故意保持小巧但有多个文件依赖，目的是：

- 修改任一功能时，模型不得不同时读多个相关文件，上下文才会真正膨胀。
- 不同的子命令分布在不同类里，便于在多轮对话中制造"跨文件理解"的负担。
- 测试文件可以充当"真实验证手段"，让"是否完成任务"有一个客观信号。

## 3. 十轮长上下文对话设计

每一轮都遵循统一结构：**任务指令 → 触发上下文膨胀的动作 → 压缩触发 → 下一轮准备**。为了让每一轮都逼出压缩，模型在每一轮中应当被引导执行"大量读文件 + 大段工具输出 + 长篇解释"三件套。

### 第 1 轮：项目全景勘察

任务：让模型读取整个 mock 工程，包括所有源文件、测试文件、`pom.xml`、`README.md`，并输出一份"功能全景 + 可改进点清单"。

触发膨胀的方式：要求模型按文件逐个调用读文件工具，输出完整内容，并要求它在最后给出不少于若干条改进建议的长文本总结。这一轮结束后，静态层（项目背景）与动态层（输出文本）都会显著增长。

预期压缩触发点：本轮结束后上下文应接近压缩阈值但不一定触发压缩，作为基准。

### 第 2 轮：跨文件依赖分析

任务：要求模型画出"当前各文件之间的调用关系 + 数据流向 + 潜在耦合点"，并以长篇文字解释。

触发膨胀的方式：要求模型再次调用读文件工具，并产出结构化长文（每个调用关系附说明，每个耦合点列风险与改进方向）。

预期压缩触发点：动态层文本继续累积，本轮末或下一轮开始时大概率触发第一次压缩。

### 第 3 轮：第一次重大重构

任务：让模型把 `NoteStore` 中的"笔记存储数据结构"从当前的简单实现替换为更清晰的分层（例如分离出 ID 生成、时间戳、持久化接口），并同步修改 `CommandHandler` 与 `Main` 的调用。

触发膨胀的方式：要求模型先贴出重构设计文档（长篇），再分多次编辑文件，每次编辑后输出 diff 摘要。修改面涉及三个文件，工具输出累积。

预期压缩触发点：上下文已经远超单轮阈值，模型会自动触发压缩。

### 第 4 轮：补充单元测试

任务：要求模型为第 3 轮重构后新增的接口补全单元测试，运行测试并贴出完整输出。

触发膨胀的方式：测试结果输出常常很长，加上 diff、错误堆栈等，会把动态层进一步撑大。

预期压缩触发点：本轮中或末段一定触发第二次压缩。压缩后必须保留"重构目标 + 当前接口形态"等关键信息，否则后续轮次会出现目标漂移。

### 第 5 轮：修复测试暴露的 Bug

任务：让模型根据第 4 轮测试中失败的用例，定位并修复 `CommandHandler` 中的逻辑错误。

触发膨胀的方式：要求模型先复述失败用例、给出根因分析、列出候选修复方案，再执行修复并重新跑测试。这一轮里"上一次失败的堆栈 + 候选方案讨论"会形成大段历史。

预期压缩触发点：必须触发压缩。压缩质量评估点：模型是否还能记得"重构目标尚未完成"以及"现在是修 bug 阶段，不是重新设计"。

### 第 6 轮：新增子命令

任务：在现有 CLI 框架中新增一个子命令（例如"按关键字搜索笔记"），要求模型自行决定要修改哪些文件、实现哪些方法、补哪些测试。

触发膨胀的方式：模型需要回顾前面的实现（被压缩后只能靠摘要）、新增代码、补充 README。这一轮是"压缩后语义恢复能力"的关键检验。

预期压缩触发点：本轮中段或末段触发压缩，压缩摘要中应保留"已有子命令集合"和"重构后的接口形态"。

### 第 7 轮：引入配置文件

任务：让模型把硬编码的某些默认行为（如默认笔记条数上限）移到配置文件中，并支持从命令行覆盖。

触发膨胀的方式：要求模型输出配置文件设计、兼容性说明、迁移步骤，工具调用次数增加。

预期压缩触发点：本轮末触发压缩。压缩摘要应保留"重构目标仍未完成"与"配置文件位置待确定"等关键状态。

### 第 8 轮：错误处理强化

任务：让模型为 CLI 增加统一错误处理（参数解析失败、文件 IO 异常、空输入等），并修改 `Main.java` 让所有子命令走统一错误出口。

触发膨胀的方式：错误处理往往要遍历多个分支，模型需要先列出所有错误路径，再实施修改，文本与代码 diff 都很长。

预期压缩触发点：本轮触发压缩，测试目标与重构目标的保留情况是核心评估点。

### 第 9 轮：性能与代码风格整理

任务：让模型对整个工程做一轮"小优化 + 风格统一"，包括提取重复代码、统一命名、统一日志格式。

触发膨胀的方式：模型需要回顾大量已修改文件，输出一致性报告，再做批量修改。

预期压缩触发点：本轮触发压缩，模型如果丢失前面"重构目标 = 分层 + ID 生成 + 时间戳 + 持久化接口"将直接表现为止步不前。

### 第 10 轮：收尾验证

任务：要求模型重新阅读所有源文件与测试，跑一遍完整测试套件，并输出一份"本次改造总结 vs 最初目标"的对照清单。

触发膨胀的方式：完整测试输出 + 总结文档 + 跨文件回顾。压缩机制是否把第一轮的"项目全景 + 改进清单"与第三轮的"重构设计"都保留下来，决定了这份对照清单的准确度。

预期压缩触发点：本轮可能继续触发压缩，但此时任务已接近收尾。压缩后是否能稳定输出对照清单是终局评测。

## 4. 任务完成判定标准

整体目标：完成第 3 轮设定的"将 NoteStore 改造为分层结构"重构，并且在第 4 至第 10 轮中所有新增 / 修改 / 修复都基于这个目标，没有发生任务漂移。

判定方式（建议用三层信号）：

- **行为信号**：跑 mock 工程自带的所有单元测试，全部通过。如果有新增测试或新增子命令，也需要通过对应验证。
- **代码信号**：在最终源码中能直接看到分层接口（ID 生成、时间戳、持久化接口三者独立），并且 `CommandHandler`、`Main` 调用的是新接口而非老实现。
- **对话信号**：第 10 轮输出的"本次改造总结 vs 最初目标"对照清单中，"分层结构"条目应被显式标记为已完成；其它条目应被回溯到对应的轮次。任何在第 10 轮中出现"我好像忘了最初的目标"或"这个改动跟原任务无关"的表述都算压缩失败。

任务完成 / 失败的判定由人工 + 自动验证共同完成：

- 自动验证：执行 mock 工程的测试脚本，断言通过。
- 人工验证：阅读第 10 轮对照清单与最终 diff，确认无目标漂移。

## 5. 三个核心测量指标

### 5.1 十轮对话平均 Token 压缩率

定义：压缩率 = 压缩前 token 数 / 压缩后 token 数。

计算方式：

- 每一轮结束后记录"压缩前上下文总 token 数"与"压缩后上下文总 token 数"。当某轮没有触发压缩时，记为 1.0（视为无变化）。
- 把十轮数值求算术平均，得到"平均压缩率"。
- 同时记录"触发压缩的轮次占比"，作为辅助指标（若该占比过低，说明本训练集设计强度不够，需要让每一轮都强制触发压缩）。

数据来源：从 J-Coder 的上下文层日志里取数；如无现成指标，可以用字符数 ÷ 4 估算（中英文混合场景下偏保守但稳定）。

### 5.2 十轮对话中的最高压缩率

定义：在所有触发了压缩的轮次里，挑出压缩率最大的一次，作为"最高压缩率"。

用途：

- 反映系统在最极端情况下的压缩能力上限。
- 若最高压缩率过低（例如全部低于 2 倍），说明压缩机制过于保守，可能存在压缩阈值过高或摘要策略不够激进的问题。

附带记录：最高压缩率出现那一轮对应的"压缩前主要构成"（例如"大量历史堆栈 + 候选方案"），便于后续调优。

### 5.3 完成任务的总 Token 消耗对比

定义：在"压缩开启 / 压缩关闭"两种模式下分别跑完十轮对话，直到任务完成（或失败止损），记录"完成任务总消耗 token 数"。

计算方式：

- 总消耗 token = Σ（每一轮输入 token + 输出 token + 工具调用结果 token）。
- 用字符数估算时，建议统一除以一个固定系数（如 3.5 ~ 4）来近似 token。
- 任务完成所需的真实轮数 R_complete 也应一并记录：压缩开启后有可能用更多轮次"重新理解"，也有可能反而更省轮次。

对比维度：

- 完成度：压缩开启后是否最终完成任务（是 / 否）。
- 任务完成轮数 R_complete。
- 总 token 消耗 C_total。
- 单位完成成本 = C_total / R_complete（反映每轮效率）。

理想结果是：压缩开启后任务仍能完成，并且 C_total 显著低于压缩关闭时的版本；同时 R_complete 不出现明显膨胀。

## 6. 对照实验设计

为了把"压缩机制本身"这个变量隔离出来，建议做以下三组对照：

- **A 组（开启压缩）**：J-Coder 默认运行，跑完十轮对话并完成目标。记录压缩日志、token 消耗、最终代码状态。
- **B 组（关闭压缩）**：在同样的对话脚本下，通过配置把压缩层禁用（例如把摘要阈值调到无限大，或绕过摘要器直接拼接原文）。其它层（静态层、记忆层、任务层）保持不变。
- **C 组（人工限长）**：模拟一个"朴素基线"——当上下文接近模型窗口上限时，直接截断最早的历史，只保留最新若干轮。该组用于对比"压缩摘要"是否优于"粗暴截断"。

每组都使用同一份对话剧本（同样的用户指令、同样的工具调用顺序、同样的中间产物），保证差异只来自压缩策略本身。

## 7. 数据采集与日志约定

为了保证三个指标可复现，建议训练集运行过程中收集以下日志：

- 每一轮的"压缩前 token 估算"与"压缩后 token 估算"，最好带分层标签（静态层 / 动态层 / 工具结果层 / 摘要层）。
- 每一轮被摘要的内容类型与摘要长度，例如"本轮摘要覆盖了 3 段工具输出 + 1 段模型解释"。
- 每一轮"用户指令"的字面文本，方便事后复盘是否出现目标漂移。
- 第十轮结尾的"目标对照清单"原文。
- 最终代码 diff 与测试运行结果。

日志格式建议为结构化 JSON，便于后期脚本统计；如项目本身已有上下文层日志体系，优先复用。

## 8. 注意事项

- **保证每一轮都能触发压缩**：十轮中如果压缩触发轮次少于 6 轮，说明剧本"密度"不够，应在剧本中加入"要求模型输出长篇总结 / 要求读取大文件 / 要求列出全部候选方案"等显式动作。
- **避免用户侧主动精简上下文**：用户在十轮中只发任务指令，不主动要求"忽略历史 / 重新总结"。任何对压缩的干预都由系统自动完成，以保证评测的是压缩能力本身。
- **任务目标必须显式锚定**：第一轮中就把"重构目标 = NoteStore 分层化"用一句话写明，并在每一轮剧本里以"请基于上述重构目标"开头，便于事后判断是否漂移。
- **不预设实现细节**：剧本只描述任务与产出，不写具体代码，避免污染被测模型的实现选择。
- **可重复执行**：对话剧本应写成结构化清单（轮次、指令、期望产物、压缩触发条件），让同一份剧本可以在 A / B / C 三组中重复运行。

## 9. 交付物清单

完成本训练集后，建议产出以下文件：

- `eval/fixtures/mock-project/`：受试用的命令行记事本工程。
- `eval/scripts/run-round.sh`：跑某一轮对话的小工具，输入轮次与模式（开启压缩 / 关闭压缩 / 朴素截断），输出日志。
- `eval/scripts/aggregate.py`：读取日志，计算三个核心指标并输出对比表。
- `eval/test.md`：本文件，作为方案说明。
- `eval/results/<date>/`：每次实验的原始日志与指标 JSON。
